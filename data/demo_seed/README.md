# Demo Seed Data

Tracked, immutable input for the synthetic demo profile (`var/demo/`,
built by `make demo` / `scripts/build_demo_profile.py`).

## Contents

- `mock_bmo_chequing.json`, `mock_bmo_mastercard.json`,
  `mock_investment_statement.json`, `mock_manual_asset.json` — synthetic
  importer-JSON statements, in the same shape produced by the real PDF
  importers (`app/services/importers/`) *after* parsing, but hand-authored
  here rather than parsed from an actual PDF.
- `categories_demo_seed.json` — a synthetic `categories_custom.json`,
  covering every categorization code path (authoritative corrections,
  soft corrections, plain seeds, fuzzy variants, and at least one
  unmatched transaction). Generated by `scripts/generate_mock_categories.py`
  and committed here as a fixed input — `make demo` applies it as-is; it
  does not regenerate it.

These files are never written to by `make demo` or any test. If you add
or change a mock statement, re-run
`venv/bin/python scripts/generate_mock_categories.py` (after building an
ingest-only demo profile so it has transactions to read) and commit the
regenerated `categories_demo_seed.json`, then update `EXPECTED_BASELINE` in
`tests/test_build_demo_profile.py` to match the new build output.

## Why this is enough for the default demo path (Tier 1)

`make demo` ingests these JSON files directly through
`app.services.normalize_parquet.ingest_pdf_with_importer_json()` — it
never parses a real PDF. That means the default demo path has **no
dependency on Camelot or its system package (ghostscript)**, even though
`requirements.txt` lists `camelot-py[cv]` for the real importers. If
`make install` fails on the Camelot line in an environment without
ghostscript, the demo/dashboard still works once that one dependency is
resolved separately (`sudo apt-get install ghostscript python3-tk` on
Debian/Ubuntu) — it is only required for importing an actual bank PDF via
`/import`, not for `make demo`.

A second tier — synthetic *PDF* fixtures that exercise the real
Camelot/pdfplumber parsing code end to end — is future work, not part of
this directory; see the design plan's Milestone 4.
